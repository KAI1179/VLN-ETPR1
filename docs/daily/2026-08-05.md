# 2026-08-05

## Oracle-t0 pretraining navigation cache 吞吐诊断

用户观察到 `oracle-t0-pt-cache` 的 tqdm 预计总耗时约 70–90 小时，login node
`jbs 1217073` 显示 8 张 GPU 利用率仅约 56%–64%。现场复核时，作业已运行
22:51:34，各 worker 只完成约 26%–28%，单条约 40–70 秒；8 张 GPU 的负载和
进度相近，因此不是单 worker 卡死或 GPU shard 错配。

根因是新 launcher 遗漏 `--batch-size 8`，回退到 CLI 默认 `batch_size=1`。历史
ordinary pretraining cache launcher 明确使用 batch 8；当前作业的实际吞吐与历史
Oracle navigation-full batch-1 作业一致：后者首轮 8-GPU 作业 `1202940` 在
24:27:12 内生成约 1.3 万条，当前 `1217073` 在约 23 小时也生成约 1.3 万条。
当前 prediction 平均约 2.6 KiB，与历史 Oracle navigation-full 的 2.59 KiB 接近，
且小于 ordinary cache 的 3.19 KiB，因此 dataset 规模和输出变长不是主要回归。

另发现原作业已经记录 502 个 `grid_parse_or_write_failed`、3 个
`input_too_long` 和 1,225 个 preprocessing `skipped_input`。后者也存在于 ordinary
cache population。若 `pretrain-only` 继续沿用 navigation-full 的“任何逐条失败均使
parent 非零退出”语义，则完整遍历后仍无法进入已经预注册的 strict intersection
cohort。修正后的 contract 为：

- worker crash、未捕获异常、缺失 shard metrics 仍显式失败；
- 每条无效生成继续保存 typed failure status，不做 silent repair；
- `navigation-full` 仍对任何 skipped fail closed；
- `pretrain-only` 完整遍历可以成功结束，随后只由 hash-pinned ordinary/Oracle
  complete intersection 决定两个 PT arm 的共同 population。

## batch resume 与 OOM splitter 修正

用户明确批准在确认修复后停止并重启 cache。原 batch-1 作业 `1217073` 于运行
23:02:04 后取消；已有 complete status/raster 原样保留。第一版 batch-8 resume
`1222241` 暴露了既有 `generate_with_oom_splitting` 的真实缺陷：helper 在
`except torch.cuda.OutOfMemoryError` block 内递归，异常 traceback 持有失败 batch
的 CUDA tensor；因此 8→4→2→1 后，size-1 retry 仍因只剩几十 MiB 而 OOM，8 个
worker 全部退出。

修复后先退出 exception handler、回收 Python traceback/tensor，再执行
`torch.cuda.empty_cache()` 与递归 split。新增回归测试在 `empty_cache` 时断言失败
allocation 已释放；本地 focused 19 tests、Ruff、ty 通过，execution host 同一
focused suite 为 19 passed。相关提交：

- `379388c`：恢复 batch 8，并明确 pretrain-only/cohort completion contract；
- `8c493a1`：按 cluster 规则为短时 cohort dispatcher 申请 1 GPU；
- `dcf72ca`：在 split retry 前释放 OOM traceback/CUDA state。

修复 splitter 后的 batch-8 real-load 作业 `1222245` 正常从 OOM 恢复，GPU compute
利用率由 batch 1 的约 60% 提升到 97%–98%。首轮 8 个 batch 中有 7 个发生一次
8→4 split，但没有 4→2 split；因此实际显存边界是 batch 4，继续请求 batch 8 只会
增加失败 prefill 与 allocator 开销。launcher 最终固定 `--batch-size 4`，提交为
`4a61b04`。

最终 resumable cache 作业为 `1222283`。其成功后，`afterok` dispatcher
`1222284` 会冻结
`pretrain-mixed-llm-grid-ordinary-oracle-t0-common-v1.json`，计算 artifact 的精确
SHA-256，并用该显式 pin 提交 ordinary 与 Oracle 两个 4-GPU matched PT arm。
当前没有启动 DAgger、GRPO 或 YOLOE。

`1222283` 于 17:06:31 CST 启动，约 8 分钟 annotation scan 后进入 generation。
前 10 分钟各 worker 完成 3–5 个 batch（每 batch 4 条），累计约 35 个 batch；按
aggregate rate 外推约 40 小时，考虑当前样本不足 1%、worker 间长输出差异较大，
采用 **35–50 小时 remaining** 的保守区间，即预计约在 8 月 7 日 04:00–19:00 CST
完成。该区间会随 tqdm smoothing 收敛，不能把单个长输出后的瞬时 45–60 小时
读数当作稳定 ETA。

两次 `jbs` snapshot 中，8 张 GPU 的 compute utilization 分别为 77%–99% 与
75%–98%，第二次有 7/8 张达到至少 85%；这验证了 batch-1 skinny decode 是原约
60% utilization 的主因。前 35 个 completed batch 中共出现 4 次 4→2 OOM split，
均自动恢复，未出现 worker crash；因此 batch 4 仍是当前吞吐与显存风险的合理
平衡点，不再为追逐早期 noisy ETA 重启作业。
