### 诊断

各 rank 的 rollout 结果正常，但旧聚合逻辑从本 rank 的 episode 统计中独立生成 metric key
列表，再逐 key 调用一次 `all_gather`。rank 0 因无 cache 缺失只有 11 个 key；rank 1–3
因包含 `llm_cache_missing` 和 `llm_generation_failure` 而有 13 个 key。

四个 rank 在前四次 collective 后开始用不同 metric 和不同 dtype 的标量参与同一
`all_gather`，导致聚合值损坏；rank 0 完成较短的 11 次调用后写出聚合 JSON 和 rank 0
JSON，rank 1–3 则阻塞在额外的两次 collective，无法写出各自 JSON。作业因此在打印
最终报告后仍持续运行。异常聚合 JSON 不可使用。

由各 rank 在 collective 前记录的正常均值加权重建得到：

- `steps_taken`: 99.796629
- `success`: 0.654160
- `spl`: 0.552537
- `ndtw`: 0.641457
- `path_length`: 14.095818
- `llm_cache_missing`: 6 / 1,839 = 0.003263

这些重建值仅用于诊断；缺少 rank 1–3 的 episode 级 JSON，因此仍需修复后重跑。

### 修复与验证

共享评估器现先通过一次 object collective 获取全局 metric key 并排序，再把 episode
数与各 metric 的本地和打包成一个固定 `float64` 向量，只执行一次 `all_reduce`。
每个 rank 写出 episode JSON 后增加 barrier，确保 rank 0 只在全部 rank 文件落盘后
写聚合结果和打印最终报告。

回归测试覆盖：

- 一个 rank 无 LLM failure metric，另一个 rank 有两个 failure metric；
- Python float、NumPy float32 和 NumPy float64 混合；
- 两个 rank 生成相同 schema、shape 和 dtype 的 collective 向量；
- 两个 rank 得到相同的总 episode 数和加权聚合结果。

验证结果：

- `tests/etp_llm/test_navigation_scaffold.py`: 10 passed
- `ruff check`: passed
- 新增测试文件 `ty check`: passed
- 共享 legacy trainer 仍有 38 个与本次修改无关的既有 `ty` 诊断；新增聚合代码无诊断
