# 06｜视觉语义缓存与损失监督核对

核对日期：2026-08-13

适用对象：05 方案的当前 `online_fusion` 实现

## 0. 结论

1. “全量视觉语义缓存”是用 Habitat 在 MP3D 全部有效 viewpoint 渲染 12 个方向的 Depth + Semantic，再保存为逐 viewpoint 的 37 类可见语义标签。它只监督 `VisualEvidenceHead`，不是模型输入，也不是认知地图 GT。
2. OnlineFusion 定义了 **5 组辅助 loss**：`grid/state/visual/progress/ghost`。正式配置中，预训练启用全部 5 组；DAgger 冻结 `VisualEvidenceHead` 并关闭 `visual`，实际为 action 加其余 4 组。
3. 当前进度监督可以学习“沿 GT 路径走到几成”的代理量，但不是语言子任务完成度。`off-route` 是当前状态，`recovery` 是逐 ghost 的候选动作标签，二者不能等同。

## 1. 全量视觉语义缓存

### 1.1 如何生成

在 `etpr1-py38` 环境中执行：

```bash
CUDA_VISIBLE_DEVICES=6 \
bash scripts/local/generate-online-fusion-visual-evidence.sh \
data/online_fusion/panorama_semantics_v1.hdf5
```

生成流程：

1. 遍历 `pretrain_src/datasets/R2R/connectivity/*_connectivity.json`；默认覆盖 90 个 scan、10,567 个 `included=true` viewpoint。
2. 对每个 viewpoint 加载对应 MP3D `.glb` 与 semantic annotations。
3. 用 Habitat 渲染 12 个水平朝向：`0°, 30°, ..., 330°`；每路包含配对的 Depth 和 Semantic，分辨率 `256×256`、HFOV `90°`、相机高度 `1.25 m`、Depth 范围 `0～10 m`。
4. 收集有效深度像素中出现的语义实例，映射为 `27 object + 10 region` 的 37 维 multi-hot 标签。
5. 写入 HDF5：key 为 `<scan>_<viewpoint_id>`，value 为 `(37,) float32`；先写 `.tmp`，完成后再原子重命名。

该生成器是**单 GPU 串行**程序；暴露多张 GPU 不会自动并行。

当前状态：默认文件 `data/online_fusion/panorama_semantics_v1.hdf5` **尚不存在**，因此正式预训练启动器会直接报缺失并退出。

### 1.2 用途

它只提供“这个 panorama 看见了哪些类别”的训练 GT：

```text
visited 拓扑节点表示 → VisualEvidenceHead → 37 类 logits
                                        ↕
                         panorama 37 类 multi-hot GT
```

- 预训练使用离线 RGB/Depth feature、没有实时 simulator，因此从该 HDF5 读取 visited viewpoint 标签。
- DAgger 不读取该 HDF5，不启用 Semantic sensors，并冻结预训练后的 `VisualEvidenceHead`。
- 验证/推理不计算 `L_visual`；语义 GT 不送入导航网络。
- 它不是 LLM-Grid 缓存、RGB/Depth feature 缓存或 `(37,100,100)` 认知地图 GT，也不包含语义位置、数量和置信度。

## 2. 当前一共有几个 loss

### 2.1 计数方式

- OnlineFusion 本身：定义 **5 组加权辅助 loss**。
- 整个预训练：跨任务共 **7 类**，即 `MLM + SAP + 5 组辅助 loss`。MLM/SAP 使用交替 batch，一个 batch 只计算其中一个主任务。
- 正式 DAgger：实际启用 **5 组**，即 `action + grid/state/progress/ghost`；`visual=0`。

正式启动脚本使用的阶段权重为：

```text
预训练：λ_grid=0.3, λ_state=0.05, λ_visual=0.2,
λ_progress=0.1, λ_ghost=0.1

DAgger：λ_grid=0.3, λ_state=0.05, λ_visual=0,
λ_progress=0.1, λ_ghost=0.1
```

### 2.2 GT 与具体形式

| loss | 形式 | 监督来源 | 是否有 GT |
|---|---|---|---|
| `L_MLM` | masked-token CE | 被 mask 前的原始 token | 有，自监督；仅 MLM batch |
| `L_SAP / L_action` | action CE | 预训练的 GT next node；DAgger 的 simulator expert action | 有，GT/expert 派生 |
| `L_grid` | masked focal BCE + Dice | `gt.legacy.r1p5.direction5.v1` 的完整 episode 认知地图 | 有，但 GT 稀疏；有效 mask 是正格及其半径 2 邻域，不把全部 0 当负例 |
| `L_state` | 地图残差 L2 + 写门预算 + token 多样性约束 | 无 target | **无 GT，是正则项** |
| `L_visual` | 类别平衡的 masked BCE | 12-view Habitat/MP3D panorama 37 类语义 presence | 有；仅预训练启用，DAgger 关闭 |
| `L_progress` | phase CE + route-state CE + remaining SmoothL1 + recovery 类别平衡 BCE | GT trajectory、目标距离和 ghost 真实候选位置派生 | 有 GT 依据，但属于规则生成标签 |
| `L_ghost` | expert ghost 上的 CE | SAP global action 或 DAgger teacher action | 有，expert 派生；teacher 为 STOP/无效动作时不计算 |

补充限制：

- 预训练只含 expert-path prefix，不产生 off-route 样本，所以 `recovery` 全部被 mask；真正的 off-route/recovery 监督只来自 DAgger。
- MLM 使用完整 expert path，`phase` 被忽略、`ghost` 无 expert action，因此这两部分在 MLM batch 没有有效梯度。
- 当前没有 JSON/文本地图 loss，也没有“视觉支持/想象/认知错误”分类 loss。

## 3. 进度预测如何训练

### 3.1 预测与损失

共享进度表示由 instruction、visited 节点、当前节点和更新后的认知地图共同产生，再预测：

```text
phase：5 类                     → CrossEntropy
route state：on/off/finished    → CrossEntropy
remaining：[0,1]                → SmoothL1
recovery：每个 ghost 一个 logit → masked class-balanced BCE
```

四项直接相加后统一乘 `λ_progress=0.1`。共享进度表示还进入 ghost/STOP 动作残差，因此导航 action loss 也会反向影响该表示。

### 3.2 DAgger 标签定义

判定顺序如下：

1. 当前位置到目标的 geodesic distance `<1.5 m`：`finished`，`remaining=0`。
2. 否则，当前位置到整条 GT path 的最小 geodesic distance `>3 m`：`off-route`；`phase/remaining` 被 mask。
3. 其余为 `on-route`：在不早于历史进度的 GT path 后缀中找最近点，令
   `p=path_index/(path_length-1)`，再取 `phase=min(4, floor(5p))`、`remaining=1-p`。

因此当前学到的是**GT path 索引进度**，不是指令中“第几个语义子任务已经完成”。

### 3.3 off-route 不等于 recovery

不等于。两者处于不同层级：

- `off-route`：描述 agent 当前离 GT path 超过 3 m，是 episode 级状态；它完全可能来自单纯走错。
- `recovery_g`：仅在已经 off-route 时，判断 ghost `g` 是否可能把 agent 拉回路线，是候选动作级标签。

当前代码把 ghost 标成 recovery 正例的条件是：

```text
ghost 到 GT path 的距离 ≤3 m
或
相对当前位置至少缩短 0.25 m
```

所以一次走错可以对应：`route_state=off-route`，同时所有 ghost 的 `recovery=0`；若 ghost 没有可靠真实位置，则 recovery 直接 mask。teacher action 也不会自动被当成 recovery。

### 3.4 能否学到进度：结论与问题

**可以学习到粗粒度路线进度，但当前形式不能保证学到真正的任务执行进度。**原因是：

- phase CE 与 remaining SmoothL1 同时给出离散、连续监督，训练信号成立；
- 但 path 点间距不一定均匀，`path_index` 比例不等于实际行进距离比例；
- step embedding 和 visited 数量可能成为“走了多少步”的捷径；
- off-route/recovery 只在 DAgger 学习，效果依赖 rollout 中是否产生足够偏航样本；
- 当前 `0.25 m` 条件只说明“朝路线靠近”，命名为真正的 recovery 偏强，并且它比较的是整条 path，可能鼓励回到已经走过的旧路段。

直接建议：

1. 保留现有四个 head，不增加“走错”新类别；`off-route` 已经覆盖走错状态。
2. 将 phase/remaining 的 `p` 改为 GT path **累计 geodesic 长度比例**，比 waypoint index 更准确。
3. 将 recovery 理解或命名为 `recovery_candidate`；若要求“真正恢复”，正例应至少回到 `3 m` 路径带，并限制回到当前进度附近或之后的 path 段。
4. 单独记录 phase accuracy、route-state F1、remaining MAE、recovery PR/F1；仅看合并后的 `L_progress` 下降，不能证明进度已经学会。
